- Cotality has exactly two kinds of Media rows: Photo and FloorPlan. Video, branded tour, unbranded tour, 3D, documents are NEVER Media rows; video and every tour are URL strings in `Property.VirtualTourURLBranded/Unbranded(2,3)`.
- Mallan's read side (public page, `/api/listings`, DTO) already implements the Cotality shape for Cotality listings and works live (photos, floor plan, YouTube embed, Matterport embed all rendered for RLS20114301).
- The WRITE side for Mallan-created listings is broken in every form: only 1 of 6 tour/video controls reaches a canonical key; photo/floor-plan upload cannot complete (route unreachable on this dev server and R2 is not configured); rental forms, both "WITH-TOOLS" forms and both deal forms have no working media at all.

### Canonical Cotality-shaped contract the forms must conform to
1. Photos and floor plans -> `listing_media` rows (Mallan key `crm:{listing}:{hash}`), `media_type` Photo|FloorPlan, `media_category` same, `media_classification` `PHOTO` / `DOCUMENT` (uppercase like Cotality; CRM currently writes `null` / `Document`), `order` per class, one `preferred_photo_yn`.
2. Video, branded tour, unbranded tour(s), 3D -> ONLY `raw_data.VirtualTourURLBranded`, `VirtualTourURLUnbranded`, `VirtualTourURLUnbranded2`, `VirtualTourURLUnbranded3` (what `lib/idx/db-to-public-dto.ts:604-609` reads). No other key name is read by any public surface.
3. Video vs 3D is decided by HOST at display time (lib/media/listing-media-resolver.ts:867-930). A host that cannot be embedded must render as a link, not an iframe.
4. Documents: Cotality has none; Mallan documents are internal (deal/transaction documents) and must not be presented as listing media.
5. Third-party (Cotality) media on any form is read-only, always with provenance/attribution.

## 4. THE UPLOAD ROUTE: defect or dev artifact?
`POST /api/crm/listings/[id]/media/upload` (also `media/[mediaId]` GET/DELETE/PATCH): **dev-server routing artifact, not a route defect.**
- Source exports `POST` only (upload/route.ts:46), compiles (chunk `.next/dev/server/app/api/crm/listings/[id]/media/upload/route.js` exists, built 15:43), identical in 1f1b5bc9 and 71381e1c.
- The running process's route table is missing it: `.next/dev/types/routes.d.ts` (written 15:50) and `server/app-paths-manifest.json` lack `/api/crm/listings/[id]/media/upload` and `/media/[mediaId]`, and 10 unrelated routes (`/api/crm/sales/prospects/[id]/{comps,convert,hook-email,outreach,pdf,pitch-packet,research,send-packet}`, `/api/crm/clients/[id]/external-listings/[externalId]` and `.../comments`); 288 route files on disk vs 276 listed. Live: all of them 404 (HTML 404 for JSON, text/plain "Server action not found." for multipart: the request falls through to the page renderer which treats a multipart POST as a server action). OPTIONS is 204 on registered routes and 404 on these.
- Invoked in-process (tsx, bypassing the router; `invoke-upload-route-noR2.json`): no session 401, buyer 403, unknown listing 404 "Listing not found", broker on SL-0030 **503 "Media storage not configured"**. With fake R2 env: 502 "Failed to store image" after image validation + Sharp optimisation. So the handler is correct.
- R2: route requires `R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET_NAME, R2_PUBLIC_URL`; none are set (no .env in the repo, not in the server environment). Without them, upload = 503 (after auth, listing and capability checks). Upload, set-main, delete therefore cannot be proven end to end here; reorder (`media-order`) was proven (200, DB order updated).
- Cause of the missing registration: not determinable from outputs (start-app.js discards stdout; `next-development.log` has no entry). Near the end of this session the dev server began returning 500 for every route (`./app/globals.css ... CssSyntaxError: Invalid code point`), so it is unstable; confirmation needs a server restart, which is out of scope.
