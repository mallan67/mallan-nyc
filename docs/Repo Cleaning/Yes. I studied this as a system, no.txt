## 5. There is a much larger provider-authority contradiction than the documentation cleanup

This is the most consequential technical finding.

The cleanup branch still contains `scripts/cotality/pull-enums.mjs`, which says the sanctioned way to generate Cotality enum truth is to parse `EnumType` values from live `$metadata`.

But the newer September 6 Search/provider work found through live verification that this assumption is not reliable for **field-published vocabularies**.

Its `lib/cotality/live-contract.ts` documents why: Cotality EnumTypes are shared, may be named differently from the field, and can over-declare values. It records that 121 Property fields publishing a vocabulary were missed by the old field-name indexing approach. The newer contract uses the **Cotality Lookup endpoint keyed by Resource + Field for published values**, while using `$metadata` for declared type information.

That means the cleanup branch and current main still sit on an **older provider-truth mechanism**, while the Search branch carries a newer provider-contract correction.

This is separate from AI documentation.

## 6. The repository's own Trestle MCP has the same provider-truth ambiguity

I studied the repo MCP rather than trusting its description.

`.mcp.json` describes `trestle-fields` as a live Cotality field/enum lookup based on `$metadata`.

The implementation does correctly map a field's declared type to its EnumType rather than simply using the field name.

But two important things happen after that.

First, when the live fetch fails, it **silently falls back to local `artifacts/metadata.xml`**. The MCP tool description nevertheless says the data is “always current — fetched live.” The returned text also says it came from live `$metadata`, without differentiating that fallback in the user-visible result.

Second, `trestle_get_picklist` takes EnumType members from `$metadata` and presents them as the field's picklist values.

That conflicts with the newer September 6 finding that **field-published Lookup vocabulary and EnumType membership are not always equivalent**.

So there are currently at least three provider-contract mechanisms represented across the repository:

old enum generator → `$metadata EnumTypes`;

repo MCP → field type mapped to `$metadata EnumType`, with local fallback;

new Search provider contract → Lookup(Resource, Field) values + `$metadata` type.

Those are not semantically identical.

## My study conclusion — without proposing the fix

The underlying problem is **not simply “too many old documents.”**

It is a four-dimensional consistency problem:

**authority drift** — several files still claim broad or canonical authority beneath the new Master Plan;

**executable drift** — probes, PR templates, tests and MCP tooling still encode the old authority/provider assumptions;

**provider-contract drift** — current main/cleanup are behind the newer September Cotality contract findings;

**branch-time drift** — the cleanup, Search work and new institutional-memory work all started from the same main but evolved independently and now contradict or overlap one another.

The September 6 cleanup did successfully establish the correct **top-level skeleton**. It did not yet establish a coherent repository beneath that skeleton.

And there is another important distinction now: **some documents should be treated as subordinate technical evidence; some are stale competing authorities; some are live machine dependencies; and some contain provider claims that have since been contradicted. Those categories cannot safely be handled as one bulk “old docs” class.**

That is where I am stopping. I have **not** prescribed what should be deleted, retained, rewritten, merged, closed, rebased or sequenced. The study phase shows those decisions need to be made from these classifications rather than from file age or filename alone.
