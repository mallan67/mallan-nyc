Search needs three independent answers, not one

This is the most important technical change.

Today the current Search branch is structurally much better than it used to be. /api/idx/search calls the canonical criteria parser and shared executor, exposes detailed provider/Mallan/page/hydration accounting, and refuses unsupported criteria instead of silently ignoring them.

The shared executor also already services Agent Search, Saved Search execution/count and alert matching, with membership/order/total/page decided centrally. Do not rebuild this engine.

Instead, verify it with three independent calculations:

Oracle	Calculates
A — Provider oracle	Direct Cotality query independently returns IDs/count for criteria that Cotality supports
B — Independent raw-row oracle	Reads complete raw provider/Mallan facts and applies a deliberately simple independent predicate
C — Mallan Search	Runs the real canonical engine

For every testable criterion:

A membership
      =
B membership
      =
C membership

and:

A/B complete count = C total

and for deterministic sorting:

A/B order = C order

The oracle must not import the production Search executor.

Otherwise you create:

buggy implementation
      ↓
shared buggy helper
      ↓
test using same helper
      ↓
GREEN

That is exactly the class of failure you have been fighting.

Add property-based and state-machine testing

Example-based tests will never exhaust professional Search.

The Search invariants should include things such as:

adding a genuinely restrictive filter cannot expand the universe;
removing that restriction cannot shrink it;
sort changes order, not membership;
pagination never overlaps;
all pages reconstruct the complete universe;
total === complete universe size;
Basic → Advanced → Basic loses no hidden criteria;

temporary Search edits do not alter Saved Search until explicitly saved;
Sale criteria cannot silently execute as Rental;
provider 400/403/429/500/timeout can never become [];
failed Cotality acquisition becomes UNVERIFIED;
one canonical listing never appears twice because a return-copy exists.

Attack the tests themselves

After the Search test suite passes, deliberately damage Search.

StrykerJS mutation testing does exactly this: it injects bugs and checks whether your tests catch them. A mutant that survives proves the tests did not distinguish correct behavior from broken behavior.

>= → >
>= → <=
true → false

exact → lower_bound
suppressed → included
Sale → Rental

Stryker can also fail CI below an explicit mutation-score threshold.

I would not run mutation testing on 300,000 lines.

And stronger than an arbitrary percentage:

no unexplained surviving mutant in the Search-critical invariant set.

Equivalent mutants can be documented explicitly.
