    = Collection(Multi.Permission)

Those are different enum types.

So taking Cotality documentation describing a Media permission such as:

and using that to question what Property.Permission means is not valid evidence.

The correct verification chain has to be:

Cotality RESOURCE
    ↓

    ↓

    ↓

Not:

That exact shortcut could corrupt Search.

There is an even more dangerous issue in authenticated Search

lib/search/engine/provider-query.ts currently adds:

StandardStatus eq 'Active'

and also:

to the provider query.

That means the supposed backend/agent Search is applying an IDX-oriented provider filter before the record even reaches Mallan's mapping/business-rule layer.

Conceptually it is doing:

Cotality
   ↓

   ↓

rather than:

That can be an architectural disaster for an agent Search.

Even without asserting the still-unverified live meaning of every ListingPermission member, the design problem is clear:

an authenticated brokerage Search should not silently become an IDX inventory search merely because the underlying entitlement is called IDX Plus.

IDX is a distribution/display entitlement.

It is not automatically the definition of what an authorized Mallan broker/agent is allowed to research.

And once Permission has 'IDX' is put in the provider query, a record excluded there can never be rescued later by correct Mallan participant/private/compliance logic.

That's the wrong boundary.

Search needs to understand the Cotality graph without becoming inefficient

The answer is not to $expand=* on every Property.

That could be slow, wasteful and expensive.

The correct architecture is to classify each Cotality relationship according to how Search actually needs it.

For instance:

PROPERTY SCALAR DATA
    retrieve in first Property query

FILTER-TIME SUBSECTION
    query/expand only when criterion requires it

RESULT-CARD DATA
    hydrate bounded fields needed for visible results

DETAIL / CMA / REPORT DATA
    hydrate after selection, not across the entire result population

COMPLIANCE DATA
    retrieve early enough that no unauthorized result can escape

BUILDING SEARCH
    operate against actual Building authority where appropriate,
    then connect its Property inventory

OPEN HOUSE
    use actual OpenHouse relationship/resource rather than trying
    to reconstruct everything from Property strings

MEDIA
    retain dedicated optimized hydration when appropriate

That preserves speed and the provider model.
