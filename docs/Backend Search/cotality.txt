Yes. It is still not doing it right.

The new matrix is useful because it exposes the failure, but I would **not let Claude start fixing from this matrix yet**. The matrix itself contains architectural mistakes.

The biggest one is this:

> “Every one of the 757 live Property fields lands in exactly one declared domain or the generator refuses to run.” 

That is the wrong model.

A Cotality field can legitimately serve **multiple Mallan business domains and multiple downstream consumers**. Forcing every field into exactly one bucket hides impact.

For example:

* `StandardStatus` affects lifecycle, DOM, permissions, Search, alerts, Saved Search, CMA and reports.
* `Permission` affects Search visibility, public display, portals, private sharing, eblast and compliance.
* `BuildingFeatures` affects amenities, building search, listing display, reports and CMA.
* `ListAgentMlsId` affects attribution, agent Search, brokerage identity, compliance and reporting.
* `VirtualTourURL*` affects media, Search facets, result cards, listing workspace and marketing.

The matrix should therefore be:

**one provider field → one primary semantic meaning → many Mallan readers/consumers**

not:

**one field → one domain.**

That alone can recreate the same “fix one place, break/miss another” problem.

There are several other serious problems.

### Building is classified incorrectly

The new matrix says:

> `Building — PROVIDER-UNAVAILABLE — 403 on this subscription` 

But the previous exhaustive live probe established something more nuanced:

> `Property.Building → Building[]` expanded successfully, while querying the Building entity directly returned 403. 

Those are **not the same capability**.

The correct contract needs separate capabilities:

```text
Building entity-set direct read:      NO / 403
Property → Building navigation:       YES
Building → Media direct relationship: must be tested through entitled path
Building → Property relationship:     must be tested through entitled path
```

Calling the entire Building domain `PROVIDER-UNAVAILABLE` can cause Claude to throw away a path Cotality actually gives you.

That is precisely the kind of subsection loss you have been complaining about.

### Provider availability and Mallan coverage are being collapsed into one verdict

The current matrix uses things like:

* COMPLETE

as one final verdict. 

That hides two completely different questions:

That is not simply `MISSING` or `PROVIDER-UNAVAILABLE`.

You need both truths.

### “All rows null” does not by itself mean provider-unavailable

Claude reports 221 fields are “provider-suppressed” and null on all 591,597 rows. 

Before those are treated as unavailable, the matrix needs to state **why each field is classified suppressed**:

* explicit Cotality Field/resource permission?
* rejected `$select`?
* rejected `$filter`?
* valid query but all-null corpus?
* omitted from entitlement?
* resource unavailable?
* current population simply happens to be null?

Those are different facts.

An exhaustive null census proves:

> **no values are being delivered today**

It does not automatically prove:

> **the subscription can never deliver this field.**

The matrix needs an evidence column for that distinction.

### Current population cannot redefine the Cotality contract

Claude says the current feed carries only:

`Active, Pending, ComingSoon, Closed`. 

But we just verified live Cotality's actual `StandardStatus` vocabulary has **11 statuses**.

Mallan must support the provider contract, even when some statuses currently have zero rows.

Otherwise the next `Hold`, `Withdrawn`, `Expired`, `ActiveUnderContract`, etc. arrives and Search fails because somebody classified it as “unused.”

So every field/value needs two separate concepts:

```text
SUPPORTED BY COTALITY CONTRACT
OBSERVED IN CURRENT FEED
```

Never collapse those.

### The real root cause is visible now: multiple `$select` authorities

This is probably the most important finding in Claude's whole report:

> “The persisting `$select` is the mapper's, not the runtime's.” 

And therefore:

* some fields exist in runtime Search;
* different fields exist in sync;
* different fields reach persistence;
* different fields reach projection;
* some values show live but disappear after reload.

That is exactly the architecture you do not want.

The fix should **not** be:

> add Branded2 here, then add Branded3 there, then patch another select next week.

The fix is:

**one verified Cotality selection authority consumed by every appropriate Property reader.**

Conceptually:

```text
COTALITY LIVE CONTRACT
        ↓
canonical entitled field selection
        ↓
 ┌────────────┬─────────────┬────────────┬────────────┐
 sync         live Search   backfill     diagnostics
        ↓
canonical mapper
        ↓
Mallan storage
        ↓
Search projection
```

There can be purpose-specific smaller selections, but they must be generated/validated against the canonical contract, not hand-maintained unrelated arrays.

Otherwise this exact defect will recur.
