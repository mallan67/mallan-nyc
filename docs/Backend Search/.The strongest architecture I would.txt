The jewels are below. Several of these are much more powerful than conventional tests.

1. SQLancer-style Search Oracles	Adapt database logic-bug techniques to Mallan Search. Build queries whose relationships must be true even when we don't know the exact listing answer.	SQLancer specifically targets wrong result sets, including omitted records, using metamorphic and differential oracles rather than relying only on known answers.
2. Test-only Reference Search Interpreter	A deliberately slow, simple, pure Search implementation used only by tests. No cache, no continuation, no optimization. It consumes canonical criteria and controlled raw records, then filters → gates → dedupes → merges → sorts.	This gives the optimized production engine an independently implemented oracle. It is analogous to SQLancer's NoREC idea: compare an optimized answer with a simpler equivalent computation. It is NOT another production Search engine.
3. Metamorphic Search Laws	Encode mathematical laws Search must obey: tightening criteria cannot add records; sort cannot change membership; page size cannot change the universe; save/restore cannot change semantics; Basic/Advanced cannot change semantics.	This finds bugs without requiring us to hand-author the expected result of 20,000 searches. Metamorphic testing was created specifically for cases where a complete test oracle is unavailable.
4. Ternary Partition Oracle	For nullable provider facts, partition an unfiltered Search into true / false / unknown or < X / = X / > X / unknown, then recombine. The union must reproduce the original universe.	This is especially suited to Cotality because null, unknown and sentinels have repeatedly caused Mallan defects. SQLancer's Ternary Logic Partitioning finds DB logic bugs through this exact class of relation.
5. Stateful Model-Based Broker Testing	Use fast-check to generate sequences: Sale → set borough → Advanced → change baths → Search → sort → next → save → reload → restore → detail → back → select → report. Maintain a tiny reference model of what state should survive.	This catches the type of Mallan bug where each operation works alone but the sequence destroys criteria/state. fast-check explicitly supports model-based/stateful testing and automatically searches sequences.
6. Automatic Failure Shrinking	When a generated 14-filter Search fails, let fast-check shrink it to the minimum reproducer—perhaps Rental + 1.5 baths + page 2.	Claude gets a tiny root cause instead of drowning in a monster scenario. fast-check generates hundreds of inputs and shrinks failures to minimal counterexamples.

NIST t-way Interaction Testing	Generate guaranteed 2-way/3-way coverage across all Search dimensions, with 4–6-way strength on dangerous clusters: workflow × status × geography × ownership × sort × paging.	Search has too many filters for exhaustive combination testing. NIST covering arrays can compress enormous interaction spaces into manageable test sets; NIST notes that faults often arise from relatively few interacting factors.
8. Closure must catch every one.	Instead of asking “do we have tests?”, ask “can the tests detect the actual bug?” Stryker automates mutation testing by changing production code and checking whether tests fail.
9. Incremental Mutation Testing	Mutation-test only changed Search code during development; full Search mutation suite at release.	Stryker supports incremental mutation testing, so this does not have to become painfully slow.

The jewel I think changes Mallan the most: Search algebra

This is the part I would prioritize above almost everything else.

Instead of writing 500 expected-output tests, define laws that any valid Search implementation must satisfy.

For canonical criteria C, listing universe S(C):

TIGHTENING
S(C AND moreRestrictiveFilter) ⊆ S(C)

RELAXATION
S(C) ⊆ S(C with filter relaxed)

SORT INVARIANCE
set(S(C, sort=A)) = set(S(C, sort=B))

PAGE-SIZE INVARIANCE
unionPages(S(C, size=20)) = unionPages(S(C, size=100))

VIEW INVARIANCE
GridUniverse = GalleryUniverse = SummaryUniverse

BASIC/ADVANCED INVARIANCE
normalize(Basic → Advanced → Basic) = original canonical criteria

SAVE/RESTORE INVARIANCE
normalize(save → reload → restore) = original canonical criteria

REFINE
S(C + refinement) ⊆ S(C)

SOURCE CONSERVATION
Final =
  EligibleMallan
  ∪ EligibleThirdPartyCotality
  − SuppressedReturnCopies

REPORT ALL
Report(AllResults).universeHash = Search.universeHash

COMPARE
CompareIDs ⊆ Search.universeIDs

SELECTION
SelectedIDs persist independent of page/view

DETAIL IDENTITY
Detail.listingIdentity = selected Search canonical identity

These properties are extremely difficult for a superficially patched system to fake.

The fourth leap: covering arrays for your enormous Advanced Search

You have far too many controls to exhaustively test every combination.

NIST's combinatorial testing work is almost ideal here. It is based on the observation that most faults arise from interactions among relatively few parameters. Their ACTS tooling can create compact t-way covering arrays, including constraints; NIST gives an example where more than 1.3 billion three-way combinations are covered by only 71 generated tests.

For Mallan I would use:

all Search criteria:              2-way + 3-way
high-risk criteria cluster:       4-way
identity/count/paging cluster:    5-way
release deep test:                selected 6-way

High-risk cluster:

Sale/Rental
× status
× geography
× ownership/subtype
× sort
× page-size/continuation

This is a much more intelligent definition of “massive testing” than brute force.

There is also one architectural change I strongly recommend

Make impossible Search states impossible to represent.

Today systems tend to have things like:

total: number;
isExact: boolean;
totalPages: number | null;

Those fields can contradict each other.

Instead:

type SearchCount =
  | {
      state: "exact";
      total: number;
      totalPages: number;
    }
  | {
      state: "lower_bound";
      lowerBound: number;
      totalPages: null;
    }
  | {
      state: "unverified";
      reason: string;
      totalPages: null;
    };

And eventually for dangerous facts:

type Fact<T> =
  | { state: "known"; value: T }
  | { state: "unknown"; reason: string }
  | { state: "unavailable"; reason: string };

Then:

unknown fee → $0
unknown beds → Studio
unknown location → Manhattan
unknown permission → allowed

becomes structurally harder to write.

That directly attacks an entire historical Mallan defect family.

New tooling I believe is worth adding

fast-check is the highest-value new dev dependency I found for this project. It is designed for JS/TS property-based testing, model-based testing, fuzzing and automatic shrinking, and it works with Jest.

StrykerJS is the second. It tests the quality of your tests, supports TypeScript/Jest and has incremental mode.

NIST ACTS is valuable as a test-generation tool, not an application runtime dependency. NIST distributes ACTS specifically for t-way test generation and supports constraints and variable-strength testing.

Playwright should remain the browser authority. Its official agent tooling now provides Planner, Generator and Healer flows for Claude Code. I would use Planner/Generator but keep the final acceptance suite immutable to the Healer.

OpenTelemetry is the right standard for the Search Flight Recorder. JavaScript traces and metrics are stable.

The standard I would set

I would not promise you that any system can make Search literally incapable of ever having a bug.

I would set a much stronger and defensible objective:

No Search semantic change, provider-contract change, UI-state change, result-universe change, or downstream-consumer divergence can silently ship unless it defeats multiple independent oracles at once.

And:

Every newly discovered Search defect becomes a permanent generative, regression or mutation test so the system becomes harder to break over time.

That is a very different engineering system from what Mallan has been doing.

Right now Claude is largely being asked to reason well.

The architecture above makes Claude operate inside a system where reasoning incorrectly produces a counterexample, a failed invariant, a surviving mutant, a mismatched universe hash, a state-machine failure, or a blocked Stop hook.

That is the level I would build toward.
