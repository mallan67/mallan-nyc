The repo already has the beginning of this. lib/cotality/live-contract.ts is a good foundation because it reads generated live Cotality pulls and treats them as the provider authority rather than hand-maintained lists. But today that authority does not yet control the whole system. Search still hard-codes query semantics, the form contract still contains legacy/internal vocabulary mixed with provider mappings, and the provider executor only understands a portion of the Cotality resource graph.

What I would build is this one enforcement stack:

Cotality Contract Compiler — the absolute provider boundary. Extend the existing live pull so it compiles not just field names and enums, but the complete authorized graph: resource, field, exact type, nullability, single/multi value, published values, $select, $filter, $orderby, navigation relationships, relation keys and whether a field can actually be queried under your subscription. Generate immutable TypeScript + JSON with a contract hash and verification timestamp. No human or agent is allowed to type a Cotality field name into business code unless it exists in this generated contract. The existing cotality:pull/cotality:verify machinery gives you a starting point.
Full Cotality Resource Graph, not “Property = one flat object.” Generate a graph describing Property and every verified navigation/subsection available to your subscription—Media, OpenHouse, Building, Rooms, UnitTypes, agent/office relations, CustomProperty and whatever else the authorized live metadata actually proves. The current provider client only accepts Property | Media | OpenHouse and has no $expand capability. Current hydration explicitly retrieves Property and Media only. That is too small a foundation for the brokerage Search you are trying to build.
One machine-readable Cotality → Mallan Mapping Manifest. Every mapping should be one record containing something like: provider resource/path, type, enum/multi rules, Mallan canonical fact, storage destination, Sale applicability, Rental applicability, input form bindings, output/display binding, Search/filter behavior, CMA behavior, transformation, provenance and REBNY/UCBA rule IDs. From that manifest, generate the mapper, validation tables, form options and Search field registry. Do not maintain five separate handwritten mappings. MALLAN_FORM_CONTRACT is moving toward this idea, but it still contains provider mappings, Mallan decisions and legacy terminology in one large hand-maintained object.
Generated Search Query Compiler. Search criteria should compile from the mapping manifest—not from humans writing OData strings. Today the Search contract supports a relatively small explicit set of status, price, beds, baths, borough, neighborhood, ownership, structure, ZIP and ID criteria. The query builder then manually emits those OData expressions and currently injects Permission has 'IDX' into every provider query. A generated query compiler should know, for every Search criterion, the actual resource/path, operator support, enum type, multi-value semantics and authorization context. Unsupported queries must refuse loudly—not silently widen or narrow results.
Sale/Rental Round-Trip Compiler and Tests. SL- and RL- remain Mallan Sale/Rental identities. Every field present on the Sale form and every field on the Rental form needs a generated trace: FORM CONTROL → NORMALIZATION → CANONICAL MALLAN FACT → STORAGE → RELOAD → EDIT → SAVE → RELOAD → SEARCH RESULT. The test should compare values, types, null semantics and enum membership—not merely assert that an HTTP request returned 200. This directly enforces your “no silent data loss” rule.
Live Differential Search Harness. This is extremely important. For each supported Search criterion, the harness should execute the canonical Search engine and independently execute the equivalent direct authorized Cotality query, then compare identities, counts, sorting and pagination. That catches problems a unit test cannot catch: unsupported provider operators, provider behavior changes, missing navigation data, silent empty results, pagination gaps and accidental filters. Add metamorphic invariants too: a stricter filter cannot increase the result set; pages cannot overlap; page N + N+1 must equal the corresponding unsliced universe; Sale and Rental cannot bleed into one another; sorting must remain deterministic.
Recorded Cotality Replay Corpus. Live Cotality changes continuously, so direct-live tests alone are not reproducible. Build a privacy-safe replay corpus containing verified edge-case shapes: Sale, Rental, Coming Soon, Pending, closed history, null-heavy records, multi-value enums, participant/member-only visibility, Mallan office listings, Building, Rooms, UnitTypes, OpenHouse, Media, agent/office relationships and malformed/rare values. Then every PR replays those provider shapes through mapping → Search → CMA → compliance. Live testing proves current compatibility; replay testing prevents regression.
Separate REBNY/UCBA Rule Engine. Do not put REBNY rules into the Cotality contract. The compliance engine should consume already-mapped facts and return explicit decisions such as publicDisplayAllowed, memberVisible, addressDisplayAllowed, submissionComplete, comingSoonAllowed, etc. Every rule should carry its REBNY/UCBA source section and tests. No invented provider fields and no RLS architecture. The chain stays: Cotality fact → Mallan fact → REBNY/UCBA rule → consumer decision.
Architecture Guard using the TypeScript AST. This is how you stop future agents from undoing the work. Write a CI scanner using the existing TypeScript compiler that fails if it sees direct Cotality HTTP calls outside the canonical provider layer, provider field literals outside generated contract/mapping files, alternate provider clients, hand-written enum arrays, Search OData assembled outside the canonical compiler, CMA directly querying Cotality, or Sale/Rental forms bypassing the form-mapping contract. Also enforce the active-tree forbidden vocabulary you have established. This should be a hard error, not a warning.
Dynamic Search Orchestrator. Build one program—something like scripts/search/search-closure-orchestrator.ts—that agents must run. It determines the impact graph from the changed mapping/resources and automatically performs the correct sequence: branch/head/clean-tree preflight → Cotality contract verification → contract compile → mapping compile → resource/subsection coverage → Sale/Rental round trip → targeted Search tests → differential Cotality tests → CMA/Saved Search downstream tests → REBNY/UCBA tests → Preview proof. It should output one machine-readable closure report. No agent decides which tests seem sufficient.
Agent Preflight/Postflight Gate. Every Claude/Codex/other agent begins with something like npm run search:agent-preflight. That program prints the current branch/head, contract hash, Cotality verification timestamp, mapping hash, supported resources, dirty-tree state and forbidden-authority counts. If those are wrong, it exits non-zero. At completion, search:agent-postflight calculates what the changed code could affect and refuses closure if required readers/writers/tests were not exercised. The agent gets to write code; the orchestrator decides whether the work is valid.
Required GitHub merge gate. Local hooks are not enough because they can be bypassed. The current Search branch itself reports protected:false. Once the foundation is trustworthy, main should require the contract/mapping/Search-closure checks before merging. An agent should literally be unable to merge a field that does not exist in the verified contract or a form change that fails round-trip proof.

There are two additional techniques I would add because Search is mission-critical. Mutation tests should deliberately change a valid Cotality field name, enum token, mapping destination and query operator and prove that the contract gate rejects each corruption. And runtime provenance tracing should attach a contract hash and query-plan ID to Search diagnostics so when an agent says “this result came from Cotality,” you can prove exactly which contract, mapping and filters produced it without logging credentials or sensitive data.
