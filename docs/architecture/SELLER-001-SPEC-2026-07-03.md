## 1. Truth rules (Maya, non-negotiable — verbatim, must be visible in the UI)

1. **Metrics are separated into five truth levels** and every displayed metric carries its level:
   - **VERIFIED MALLAN TRAFFIC** — measured on our own infrastructure (tracked views, CRM inquiries, showings, client actions).
   - **TRACKED CAMPAIGN** — attributed via Mallan-issued UTM/short links.
   - **PORTAL-REPORTED** — numbers a portal reports and the broker manually enters; relayed, not independently verifiable (manual entry later).
   - **EXTERNAL PRESENCE** — confirmed appearance of the listing on an external surface; proves exposure exists, not traffic volume.
   - **MARKET PROXY** — similar-listing context computed from our own DB.
2. **Known-vs-anonymous:** **NEVER display viewer identity unless self-identified** (logged-in client, inquiry, tracked email click). Anonymous traffic = **aggregate patterns only**. No lead names, emails, lead_ids or raw/hashed IPs in any report payload.
3. **NEVER claim competitor/portal traffic without real data.** Similar-listing context uses **PROXY metrics only** — our own DB: similar active listings count / price range / DOM / price cuts from the `listings` table.
4. **Broker-network exposure phrasing:** "**network exposure, third-party lead capture**" — where lead routing goes to the displaying broker, the report must say so; never imply those leads come to Mallan.
5. **Honesty contract:** every report includes a `data_gaps` list naming what is not yet tracked.

These rules are encoded in `lib/seller-report/build-report.ts` (truth-level definitions,
known-vs-anonymous policy string, market-proxy disclaimer, data_gaps) and locked by
`tests/runtime/seller-report-build.test.ts`.

## 2. Phase 1 — internal broker report (SHIPPED in this PR, existing data only)

**No schema changes.** Runs entirely on existing models:

| Existing model | Used for | Truth level |
|---|---|---|
| `ListingView` (`listing_views`; written by token-gated `POST /api/tracking/listing-view`) | tracked views, unique/known/returning viewers, device breakdown, 7/30-day windows | VERIFIED MALLAN TRAFFIC |
| `Inquiry` (`inquiries`, string FK `listing_id`) | inquiry counts by source, RSVP counts (`source='open_house_rsvp'`) | VERIFIED MALLAN TRAFFIC |
| `Showing` (`showings`, BigInt FK) | showings by type/status | VERIFIED MALLAN TRAFFIC |
| `ClientListingAction` (`client_listing_actions`) | sent/liked/discuss/schedule/offer counts | VERIFIED MALLAN TRAFFIC |
| `Listing` (`listings`) | market proxy: similar actives, same borough + listing_type, price band ±20%, count/median price/median DOM | MARKET PROXY |

**Surfaces:**
- `GET /api/crm/listings/[id]/seller-report` — `requireAgentOrBroker`; agent sees own listings, broker sees all (same ownership rule as `GET /api/crm/listings/[id]`).
- `/admin/seller-report/[id]` — server component, session-cookie validated (agent/broker), noindex via `app/admin/layout.tsx`. Sections: Exposure / Engagement / Inquiries / Market context (proxy) / Campaign links (not yet tracked) / Portal-reported (not yet tracked) / External presence (not yet tracked) / Data gaps.
- Aggregation: `lib/seller-report/build-report.ts` (pure, tested) + `lib/seller-report/load-report.ts` (read-only Prisma loader, 5,000-row caps).

**Known Phase-1 limits (also emitted as `data_gaps`):** current tracked views cover token-gated
email-link opens by known leads only; anonymous public-site views, gallery/floorplan/tour events,
campaign links, external presence and portal-reported numbers are all Phase 2+.

## 4. External-presence discovery plan (Phase 2, manual-first — no scraping infra required to start)

Address-variant search set per listing (derived from `lib/address/nyc-address-normalizer.ts` variants):

- `400 East 90th Street 4D` · `400 E 90th St #4D` · `400 E 90th St Apt 4D` · `400 East 90th #4D, New York, NY 10128` · listing_id twins (`SL-0007` / `RLS20099289`)
- `333 East 46th Street 2G` · `333 E 46th St #2G` · `333 E 46th St Apt 2G` · `333 East 46th #2G, New York, NY 10017` · (`SL-0004` / `RLS20093870`)

Procedure (per surface: Google/Bing, StreetEasy, Zillow/Trulia, Realtor.com, Homes.com, brokerage IDX sites, social):
1. Run each address variant + "for sale"/price as query; record URL, date, screenshot reference.
2. Record a `listing_external_presence` (or `listing_broker_network_presence`) row with `evidence_note`.
3. Run the correctness audit (§5) on each found appearance.
4. Re-verify weekly at report generation; flip `status` to `stale`/`removed` when gone.
Until the tables exist (HELD), findings live in the broker's manual checklist and are NOT shown as metrics.

## 5. Correctness-audit fields (applied to every external appearance)

Per appearance: **price** (matches current `list_price`?) · **photos** (current media set? count/hero match) ·
**attribution** (shows "Mallan Real Estate Inc." + correct license/contact per NY DOS §175.25?) ·
**unit** (correct unit number — e.g. 2G vs 2F class of error) · status freshness (Active vs stale "In Contract") ·
open-house info correctness. Result stored in `correctness` Json: `{ price_ok, photos_ok, attribution_ok, unit_ok, status_ok, checked_at, notes }`.
Discrepancies feed the weekly owner narrative ("we found your listing mispriced on X and requested correction").

## 7. Phase 2/3 surfaces

- **Phase 2 — owner portal page `/owner/listings/[id]`:** lead-session (portal) auth; owner sees ONLY their own listing (`listings.owner_client_id === session lead id`, fail-closed); same truth-level sections as the internal report minus internal-only rows (client action types collapse to aggregate "buyer interest actions"); aggregate-only viewer data (rule 2). Rendering the owner's own data is not public dissemination (cf. `lib/compliance/dto.ts` owner-view precedent), but agent PII masking still applies to any third-party data shown.
- **Phase 3 — weekly owner email:** template outline:
  1. Subject: "Your listing this week — {address}: {n} tracked views, {m} inquiries"
  2. Headline numbers (VERIFIED MALLAN TRAFFIC badge): views / unique viewers / inquiries / showings vs prior week
  3. Campaign performance (TRACKED CAMPAIGN): per-link clicks
  4. Where your listing appears (EXTERNAL PRESENCE): surfaces + correctness status; broker-network block labeled "network exposure, third-party lead capture"
  5. Portal-reported numbers (PORTAL-REPORTED, "as reported by X on DATE, manually entered")
  6. Market context (MARKET PROXY + disclaimer verbatim)
  7. Narrative paragraph (broker-written or templated) + next actions
  8. Footer: truth-level legend + data-gaps note + CAN-SPAM unsubscribe (owner-report category) + brokerage attribution (§175.25)
  Send path: reuses existing SendGrid lane; suppression respects `Lead.last_unsubscribe_at` (BIZ-012 interaction — verify before launch). Snapshot stored in `listing_owner_reports` (HELD).
