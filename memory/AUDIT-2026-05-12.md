- **At audit time (2026-05-12T17:10:50 UTC):** 88 terminal listings with `idx_display_yn=true` past the 24h removal window
- **CLAUDE.md follow-up expectation:** "may report 1 transient §2.05 violation; clears at next 3am UTC `data-retention` cron"

- **Trend:** 37 → **88 in 12 days** (≈ +4/day). Not transient; not one cron run away from clearing.

The data-retention cron at `app/api/cron/data-retention/route.ts:73-107` correctly flips `idx_display_yn=false` once per day for rows whose `status_changed_at` is >24h old AND `idx_display_yn=true`. But some non-mapper write path is producing new rows in violation faster than the cron runs.
- **Compliance impact:** Each row = 1 instance of UCBA Art. I §6 / REBNY RLS §2.05 violation (Closed Listings Removed >24h). REBNY penalty ladder: data-quality violations escalate audit-only → $250 → $250 → RLS termination.
- **Severity: HIGH.** This is the single biggest active compliance debt on the site.

## 2. USER-REPORTED — PUBLIC SEARCH BROKEN

### 2a. Address search returns 0 results (PRIMARY CAUSE)

**Symptom:** Typing an address into either (a) home-page hero search or (b) `/search?tab=*-residential&q=<address>` returns no listings even when matching listings exist in the DB.

**Root cause — JSON key case mismatch on the `address` JSONB column:**

| File:line | Code |
|---|---|
| `lib/idx/mapping.ts:28-29` | **WRITER** — stores `address: { streetNumber, streetName, ... }` (camelCase) |
| `lib/search/public-listing-db.ts:109` | **READER** — `{ address: { path: ["StreetNumber"], equals: numMatch[1] } }` (PascalCase) |
| `lib/search/public-listing-db.ts:114` | **READER** — `{ address: { path: ["StreetName"], string_contains: streetPart } }` (PascalCase) |

Prisma's `path: [...]` is case-sensitive on PostgreSQL JSONB. The query never matches a row → fallthrough to Trestle live (`app/api/listings/route.ts:377-436`). If IDX is paused or the Trestle filter doesn't translate the address, the user sees 0 results.

The mismatch is **systemic**:

- `lib/idx/mapping.ts:19-30` converts incoming Trestle PascalCase → flat camelCase before persistence
- `lib/idx/db-to-public-dto.ts:161-170` reads it back with PascalCase paths (`addr.StreetNumber`)
- `lib/search/public-listing-db.ts:107-126` queries with PascalCase paths

Two layers (DTO reader + search query) disagree with one layer (writer). The two readers are wrong; the writer matches the IDXListing type.

### 2b. Hero autocomplete silent-empty path (SECONDARY)

- `app/api/listings/suggest/route.ts:194` — autocomplete address branch is gated behind `IDX_ENABLED=true`. If env is off, no autocomplete results.
- `app/api/listings/suggest/route.ts:279` — each candidate must pass `affirmPermission(raw.InternetAddressDisplayYN)`. Charter Section 8 rule 4 confirms REBNY pre-filters `InternetAddressDisplayYN` so `null` should = displayable on this feed, but `affirmPermission()` is fail-closed and treats null as deny. The suggest route is using fail-closed semantics where the rest of the public surface uses pre-filtered semantics. **This is the same class of bug fixed in commit `0309875b` (2026-04-30) for the main listing surface, but the suggest route was not included in that fix.**

### 2c. No integration test covers `addressConditions()`

- `lib/search/public-listing-db.ts:90-129` (`addressConditions()`) has no test file. The bug above would have been caught by a single integration test that POSTs a known address and asserts ≥1 result.

**Severity for §2a + §2b: HIGH** — this is the user-reported breakage. Affects every visitor who tries to search by street address.
